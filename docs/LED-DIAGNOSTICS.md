## 1. Какое железо стоит

### Контроллер (управляющая карта)

| Параметр | Значение | Откуда известно |
|---|---|---|
| Модель | **Huidu HD-C16L** | `DeviceModel` в программе-XML, ID карты |
| ID карты на стенде | **`C16L-B25-07457`** | UDP-broadcast карты, §11 `LED-INTEGRATION.md` |
| Год выпуска | **2025** (`B25` в ID) | расшифровка ID |
| Протокол | **HDPlayer, TCP 9527** | реверс перехвата `pktmon` |
| Софт-вендор | HDPlayer **7.11.18.0**, SvnVersion 16086 | `AppVersion` в XML |
| Старый SDK (TCP 10001) | **не поддерживается этой картой** | §10 `LED-INTEGRATION.md` |
| Rotation | 2 | XML программы |
| TimeZone | 21600 (UTC+6) | XML программы |

Из логов исходного архива известны ID карт **другого поколения**: `C16L-D24-00532`, `C16L-D24-0052A`
(`D24` = 2024 г.). Под них написан архивный `ScreenService` + `SDKLibrary` — с картой `B25` они
не работают в принципе, это проверено исчерпывающе.

### Панель (сам экран)

| Параметр | Значение |
|---|---|
| Физический размер | **640 × 640 мм** |
| Разрешение | **160 × 160 px** |
| Шаг пикселя | **P4** (4 мм) |
| Модули | **8 шт., 320 × 160 мм** каждый (по 80 × 40 px), раскладка 2 в ширину × 4 в высоту |
| Цвет | RGB; картинка принимается как PNG 160×160 (RGBA colortype 6 проверен, RGB тоже) |

Отсюда все ограничения читаемости QR: на 160 светодиодов по стороне модуль QR должен занимать
**не меньше 4 px**, иначе камера телефона на улице его не разделит.

### Сеть

- Панель: `169.254.255.254` (link-local, DHCP нет), TCP **9527**.
- ПК имеет адреса на нескольких адаптерах: `169.254.211.213`, `192.168.0.167`, `172.18.128.1`
  (последний — виртуальный, WSL/Hyper-V; MAC `00:15:5D:D2:73:00`).
- Панель принимает **одно** соединение на 9527: если её держит HDPlayer, скрипт получит `ETIMEDOUT`.

## 2. Что сделано 2026-09-07 по ссылке

Исходная ссылка (статический платёжный QR Bakai):

```
https://bakai.app#00020101021132460011qr.bakai.kg010121016124201001245957013021233120008BAKAIAPP5204653853034175914Kubanychbek%20A.63048209
```

139 байт payload → QR **версии 7, 45×45 модулей** → на 160 px это **3 px на модуль**,
что ниже уличного минимума в 4 px. `makecard.js` честно об этом предупредил.

Решение — короткий редирект через tinyurl:

```
https://tinyurl.com/28q77dnn  →  301  →  https://bakai.app/#0002…8209
```

Редирект проверен: фрагмент `#…` доезжает целиком (tinyurl добавляет только `/` перед решёткой,
на разбор платёжной строки это не влияет). Новый QR:

```
QR: версия 2 (25x25 модулей), ECC L, режим Byte, payload 28 б
Рендер: модуль 6 px, белое поле 5 px, квадрат QR 160x160 px
OK: модуль 6 px — достаточно для съёмки с улицы
VERIFY OK (0 несовпавших пикселей)
```

Команда, которой это собирается:

```cmd
node makecard.js "" "" "" "https://tinyurl.com/28q77dnn" 160 160 --quiet=0 --qr-px=160 --text-frac=0
powershell -NoProfile -ExecutionPolicy Bypass -File render.ps1 -White 255 -BandWhite
node send9527.js card_rgba.png
```

> **Риск:** оплата теперь зависит от стороннего редиректора. Ляжет tinyurl — QR перестанет работать.
> Для продакшена нужен свой короткий редирект на домене банка или парковки.

## 3. ГЛАВНАЯ ПРОБЛЕМА: экран не обновляется

**Симптом (со слов оператора): скрипт отрабатывает и рапортует об успехе, но на панели остаётся старая картинка.**

### Что проверено и ОТВЕРГНУТО

| Гипотеза | Проверка | Результат |
|---|---|---|
| `cmd.exe` портит ссылку с `%` и `#` при `set /p` | тестовый .bat: `set /p URL` → аргумент в node | **отвергнута** — ссылка доезжает байт в байт (99 симв.) |
| Кадры не доходят до карты | `HD_VERBOSE=1 node send9527.js` | **отвергнута** — все **18/18 кадров получили ack** |
| Карта недоступна или занята | TCP-проба 9527 | **отвергнута** — соединение и рукопожатие проходят |
| Константное имя программы `aaaa….boo` мешает перезаписи | патч: имя `.boo` = реальный md5 XML | **отвергнута** — поведение не изменилось |
| Картинка не та или битый рендер | `verify_qr.ps1` | **отвергнута** — `VERIFY OK`, 0 несовпавших пикселей |

### Что ВЫЯВЛЕНО (главная улика)

На кадр `0x0011` карта отвечает `0x0012` — списком файлов, которые у неё есть.
Ответ **не меняется никогда**, что бы мы ни отправляли:

```
<- 0x0012 66B  |0115cb16fb611f7a0bebce23c4572b9f.768cd31e82bb58009ff9779267eddd0b.|
```

Два файла (один `.png`, один `.boo`) — это программа, которую когда-то залил **HDPlayer**.

Эксперимент:

1. Отправлен `card_rgba.png`, md5 `57454a71187dea8733383de799400ea6` → все кадры ack → список **не изменился**.
2. Отправлен заведомо другой `ruler.png`, md5 `bf408ecf3c33319abe1d88b2ffe5353d` → все кадры ack → список **не изменился**.
3. Отправлена программа с честным md5-именем `e51d555e59fff9c9c10fff27f12cb124.boo` → ack → список **не изменился**.

**Вывод: карта подтверждает приём кадров, но не сохраняет файлы и не переключает активную программу.**
`ack` в этом протоколе означает «кадр получен», а не «файл записан». Поэтому `send9527.js`
всегда рапортует об успехе — успех он не проверяет.

Отсюда важное следствие: **все сегодняшние отчёты об «отправлено на экран» недостоверны** —
факт вывода картинки на панель не подтверждён ничем, кроме ack-ов.

### Вероятные причины (в порядке правдоподобности)

1. **В сессии не хватает шага, который фиксирует запись файла.** Перехват HDPlayer, с которого
   снят протокол, мог содержать кадры, признанные тогда несущественными. Кандидаты: payload
   `0x0015` жёстко `[00 00 00 00]` (возможно, это счётчик или общий размер передаваемых файлов),
   отсутствие размера файла в `0x0017`, отсутствие явного «стереть старое».
2. **Карта не перезаписывает существующие файлы** — ровно как это было у старого `ScreenService`,
   где `UploadFile` молча не перезаписывал одноимённый файл. Тогда нужен кадр удаления перед заливкой.
3. **Карта в режиме «занято»** — держит программу от HDPlayer и не отдаёт управление чужому клиенту
   без явного «взятия управления».
4. **Регрессия после правок `send9527.js`** — файл правился 2026-09-07 17:38, а успешная проверка
   была 2026-09-05. Возможно, сломано именно в этих правках (генерация GUID заново, размер из PNG).

### Что делать дальше (по приоритету)

1. **Сверить с рабочей версией от 05.09.** Найти состояние `send9527.js` на дату успешного теста
   и прогнать его как есть. Если заработает — регрессия локализуется диффом. Проект не под git
   (`is git repo: false`), так что искать по бэкапам рядом: `*.bak`, `api-server.js.work-1722`.
2. **Снять новый перехват HDPlayer** (`pktmon` из-под администратора) в момент, когда HDPlayer
   реально меняет картинку, и **побайтово сравнить** его сессию с тем, что шлёт `send9527.js`.
   Это единственный надёжный способ найти недостающий кадр.
3. **Добавить в `send9527.js` реальную проверку успеха:** после `0x001f` переоткрыть сессию,
   запросить `0x0011` и убедиться, что md5 отправленного PNG **появился** в списке `0x0012`.
   Без этого скрипт будет и дальше врать об успехе. Это надо сделать в любом случае.
4. Попробовать вариации: `0x0015` с числом файлов вместо нулей; удаление старых файлов перед заливкой;
   имена файлов в точности как у HDPlayer.

## 4. Инструменты диагностики, использованные в этой сессии

```cmd
REM подробный лог ack по каждому кадру
set HD_VERBOSE=1 & node send9527.js card_rgba.png

REM сверка отрендеренного PNG с матрицей QR попиксельно
powershell -NoProfile -ExecutionPolicy Bypass -File verify_qr.ps1

REM увеличенное превью для глаз
powershell -NoProfile -ExecutionPolicy Bypass -File zoom.ps1
```

Проба «что лежит на карте» (рукопожатие плюс чтение `0x0012`) — короткий Node-скрипт: подключиться
на 9527, послать `0x000b / 0730 / 0410 / 000d / 040a / 000f / 0011 / 0013`, распечатать ответы.
Кадр: `[len:2 LE][cmd:2 LE][payload]`, на `0xNNNN` карта отвечает `0xNNNN+1`.

Ответы рукопожатия на стенде:

```
<- 0x000c 4B  09000001
<- 0x0731 2B  0000
<- 0x0411 2B  0000
<- 0x000e 4B  00000000
<- 0x040b 1B  00
<- 0x0010 4B  01000000
<- 0x0012 66B  <два md5 файлов, лежащих на карте>
```

Содержимое `f_0410.bin` (идентификация клиента, из перехвата HDPlayer) — открытый текст:

```
Windows,HDPlayer,dan,pb,,,_,2026-09-05_14:56:43,ethernet_32774-172.18.128.1-00:15:5D:D2:73:00,wi…
```

Там зашиты дата снятия перехвата и MAC машины. Карта это принимает (`0x0411 → 0000`),
но если она проверяет идентификацию клиента строже, чем кажется, — это ещё один кандидат в причины.

## 6. Как удалённо посмотреть, что стоит на LED-экране

### Чего карта НЕ умеет

Скан портов карты `169.254.255.254`:

```
OPEN  9527      протокол HDPlayer
OPEN  10001     старый SDK (эта карта на нём отдаёт заглушки)
n/a   80 443 8080 8000 5000 10000 23 21 5900
```

**Веб-интерфейса нет, скриншот панели карта не отдаёт.** Команды «верни картинку, которую
показываешь» в протоколе 9527 не обнаружено. Увидеть глазами содержимое экрана через сеть
напрямую невозможно.

### Что работает — `whats-on-screen.cmd`

Карта честно сообщает **md5 файлов активной программы** (кадр `0x0011` → ответ `0x0012`).
Это не картинка, но железно отвечает на главный вопрос: «доехало наше или висит старое».

```cmd
tools\hd9527\whats-on-screen.cmd
```

```
панель 169.254.255.254:9527 — подключение есть

НА ЭКРАНЕ СЕЙЧАС — программа из 2 файл(ов):
  0115cb16fb611f7a0bebce23c4572b9f
  768cd31e82bb58009ff9779267eddd0b

Наш файл card_rgba.png: 57454a71187dea8733383de799400ea6
>>> НЕ СОВПАЛО: наш файл на карте отсутствует — на экране висит СТАРОЕ.
```

Скрипт **только читает**: посылает лишь читающую часть рукопожатия до `0x0011`, без
`0x0015/0x0017/0x0019/0x001b` и без финализации, поэтому испортить показ не может.
Коды выхода: `0` — на экране наш файл, `1` — старое, `2` — связи нет. Годится для мониторинга.

### Полная картина — только камера

Отпечаток md5 говорит «сменилось или нет», но не показывает, **как это выглядит**:
яркость, читаемость QR с дистанции, битые модули, засветка солнцем. Для этого нужен
физический глаз на объекте:

- любой старый Android + приложение вроде IP Webcam → RTSP/HTTP-поток;
- или обычная IP-камера, направленная на панель.

Учитывая, что `send9527.js` рапортует об успехе, которого нет, камера на объекте —
не роскошь, а необходимый инструмент отладки. Связка «камера + `whats-on-screen.cmd`»
закрывает вопрос полностью: скрипт говорит *что* на карте, камера — *как* это выглядит.

### Про удалённый доступ

Панель сидит на link-local `169.254.255.254` в одном сегменте с этим ПК, то есть достучаться
до неё можно **только с этой машины**. Удалённая работа = удалённый доступ к самому ПК
(RDP / AnyDesk / TeamViewer), а уже с него — скрипты из `tools/hd9527/`.
HDPlayer при удалённом доступе тоже открывается, но он показывает **свой проект**,
а не то, что реально горит на панели.

### Важное наблюдение: HDPlayer запущен

На ПК обнаружены:

```
C:\Program Files\HDPlayer_7.11.18.0        HDPlayer, процесс PID 3812 — ЗАПУЩЕН
C:\Program Files (x86)\HDSet
C:\Program Files (x86)\HD2020
C:\Users\dan\AppData\Local\HDPlayer\HDPlayer\nginx\nginx.exe   слушает 9527 локально
```

HDPlayer — веб-приложение с собственным nginx, который занимает **локальный** порт 9527.
Постоянной TCP-сессии с картой он в момент проверки не держал, но:

- панель принимает **одно** соединение на 9527;
- активная программа на карте (`0115cb16…`, `768cd31e…`) залита именно HDPlayer-ом;
- периодические UDP-броадкасты по 6 байт с адресов ПК — это его пробы обнаружения.

**Перед отправкой карточки HDPlayer нужно закрывать.** Это первый кандидат на объяснение
того, почему карта принимает кадры, но не сохраняет файлы (§3).

## 7. РЕШЕНО: причина — зависшая карта, лечится перезагрузкой панели

**2026-09-07, после §3–§6.** Оператор перезагрузил панель по питанию — и всё заработало.

До перезагрузки список файлов активной программы (`0x0011` → `0x0012`) был **заморожен намертво**:
что бы мы ни слали, там оставались `0115cb16…` + `768cd31e…`, залитые когда-то HDPlayer-ом.
Карта подтверждала все 18 кадров ack-ами и не записывала ничего.

После перезагрузки — список живой и меняется от отправки к отправке:

```
отправлен ruler.png      (md5 bf408ecf…)  →  на карте: 8f6bd2e7…  +  bf408ecf3c33319abe1d88b2ffe5353d
отправлен card_rgba.png  (md5 508ecbf6…)  →  на карте: 508ecbf6267bfdcef539f9500723e0c9  +  f4a44b8042…

>>> СОВПАЛО: панель показывает именно нашу картинку.
```

### Выводы

1. **Реальная причина «экран не обновляется» — зависшее состояние карты**, а не ошибка в протоколе
   или в скриптах. Гипотезы про недостающий кадр, `0x0015`, имя `.boo` и регрессию `send9527.js`
   (§3) **не подтвердились** — код был исправен всё это время.
2. **Первое действие при «не обновляется» — перезагрузить панель по питанию**, а не лезть в протокол.
   Это уже второй случай в проекте, когда питание лечит карту (ср. §10 `LED-INTEGRATION.md`).
3. **Второй файл в списке — это программа `.boo`**, её md5 меняется при каждой отправке
   (в XML генерируются новые GUID). Первый — картинка. Совпадение md5 картинки с нашим PNG
   и есть доказательство вывода.
4. **`whats-on-screen.cmd` полностью подтвердил свою полезность:** именно он показал сначала
   заморозку, а затем — что отправка доехала. Без него `send9527.js` рапортует об успехе всегда.

### Рабочий порядок действий

```cmd
REM 1) собрать и отправить
tools\hd9527\qr.cmd                       REM или show-parking.cmd / send9527.js

REM 2) ОБЯЗАТЕЛЬНО проверить, что доехало
tools\hd9527\whats-on-screen.cmd
REM   СОВПАЛО    -> готово
REM   НЕ СОВПАЛО -> перезагрузить панель по питанию и повторить
REM   НЕТ СВЯЗИ  -> см. ниже про Deprecated-адрес
```

### Отдельная засада: link-local адрес уходит в Deprecated

В момент обрыва связи `ping` давал `General failure`, ARP-записи не было, а на адаптере:

```
169.254.211.213   Ethernet   Deprecated     <- через него шла работа
```

Отвалилась не панель, а адрес на стороне ПК: Windows пометил автонастроенный `169.254.x.x`
устаревшим (мигание линка либо адаптер решил, что появился DHCP). Лечится со стороны ПК:
`ipconfig /release` + `/renew` на Ethernet, либо `Disable-NetAdapter` / `Enable-NetAdapter`.
Нужно, чтобы адрес перешёл из `Deprecated` в `Preferred`.

Это ровно тот риск, о котором предупреждает §8 п.11 `LED-INTEGRATION.md`: **для продакшена
контроллер надо переводить на статический IP**, link-local — временное решение.

### Что из §3 остаётся в силе

Пункт 3 списка «что делать дальше» — **добавить в `send9527.js` реальную проверку успеха**
(после `0x001f` переоткрыть сессию и убедиться, что md5 PNG появился в `0x0012`) — остаётся
актуальным. Сейчас эта проверка вынесена в отдельный `whats-on-screen.js`; логично встроить
её прямо в отправщик, чтобы он возвращал ненулевой код при неудаче и вызывающий `.cmd`
не рапортовал об успехе, которого не было.
