# Интеграция с LED-экраном: QR + госномер + время + сумма

Отчёт о том, как данные об оплате парковки попадают на LED-экран под контроллером **Huidu HD-C16L**.
Составлен по исходникам `src/` и проверен на стенде. Дата: 2026-09-05.

---

## 0. Главное, что нужно понять сразу

> **LED-экран НЕ принимает HTTP.**

Контроллер HD-C16L говорит по **собственному XML-протоколу Huidu поверх TCP, порт 10001**.
HTTP появляется только потому, что между вашим бэкендом и контроллером стоит прослойка — **ScreenService**
(ASP.NET Core, `src/ScreenService`), которая принимает REST-запросы и переводит их в вызовы SDK.

```
┌──────────────────────┐   HTTP/JSON      ┌──────────────────────┐   TCP 10001      ┌──────────────┐
│  Бэкенд парковки     │  ─────────────>  │   ScreenService      │  ─────────────>  │  HD-C16L     │
│  (ANPR / касса /     │  Bearer-токен    │   :8040              │  Huidu SDK XML   │  контроллер  │
│   веб-страница)      │  <─────────────  │   (SDKLibrary.dll)   │  <─────────────  │  экрана      │
└──────────────────────┘   200 / 401/500  └──────────────────────┘   ответы/события └──────┬───────┘
                                                                                          │
                                                                                   ┌──────┴───────┐
                                                                                   │ LED 160×160px│
                                                                                   │  640×640 мм  │
                                                                                   └──────────────┘
```

Вывод для интеграции: **вы работаете только с HTTP-API ScreenService**. Ничего про TCP/SDK знать не нужно,
но нужно понимать его ограничения — они целиком определяют дизайн решения (см. §2 и §8).

## 1. Как именно передаются сумма, время, QR и номер машины

### Ключевой момент: они передаются НЕ как поля, а как готовая картинка

Контроллер не умеет «сверстать» карточку из полей. У ScreenService есть ровно один способ показать
QR-код — **отправить растровое изображение**. Поэтому:

```
сумма + время + номер + ссылка на оплату
            │
            │  рендер на СТОРОНЕ ОТПРАВИТЕЛЯ (canvas в браузере / Pillow в Python)
            ▼
      PNG 160×160 px  ──base64──>  HTTP UploadFile  ──>  файл на флеш-памяти контроллера
                                                              │
                                            HTTP SendImage ───┘──> показ на экране
```

То есть **на экран едут пиксели, а не данные**. Номер, время и сумма превращаются в текст на картинке
ещё до отправки; QR-код рисуется туда же. Контроллер получает один PNG и просто выводит его.

### Почему не `SendText`

`SendText` умеет только текст (одна область на весь экран, один шрифт) — QR им не нарисовать.
Использовать его имеет смысл только для служебных сообщений («ЗАНЯТО», «ОПЛАТИТЕ»), а не для карточки.

### Что попадает в QR-код

Содержимое QR — это **строка, которую вы сами формируете**. Обычно — ссылка на страницу оплаты:

```
https://pay.example.kg/p/ABC123
```

Либо структурированный payload, если приложение оплаты его понимает:

```
PARKING|01KG777AAA|12:35|150
```

Второй вариант — то, что `send_parking_qr.py` подставляет по умолчанию, если `--qr` не задан.

**Важно:** длина строки прямо влияет на читаемость QR (см. §6).

## 2. Что происходит внутри ScreenService (и почему это важно)

Разбор `src/ScreenService/Screens/LEDScreen.cs` и `ScreenManager.cs`:

| Факт из кода | Практическое следствие |
|---|---|
| `LEDScreen.Send()` всегда собирает **новый** `HdScreen → HdProgram → HdArea(0,0,W,H)` с **одним** элементом и шлёт `Device.SendScreen` | Любая команда `Send*` **полностью затирает экран**. Нельзя показать QR и бегущую строку одновременно, нельзя обновить «часть» экрана |
| `ScreenManager.DoAction` держит **глобальный `lock`** на всё время команды | Все запросы к сервису строго последовательны. Параллельные вызовы от бэкенда встанут в очередь |
| `UploadFile` синхронный, ждёт до **5 минут** внутри этого же лока | Долгая заливка блокирует весь сервис. Для PNG 160×160 (~1–3 КБ) это доли секунды, но видео так слать нельзя |
| `UploadFile` пишет в `UPLOADS/<DeviceID>/` **только если файла ещё нет** (`if (!File.Exists)`) | **Повторная загрузка файла с тем же именем молча не перезапишет его** — экран покажет старую карточку. Перед каждым `UploadFile` обязателен `DeleteFile` |
| `DoAction` с неизвестным/пустым `DeviceID` просто не находит экран | Вернётся **200 OK**, но ничего не произойдёт. Всегда проверяйте `GetDevices` |
| Любое исключение SDK ловится и отдаётся как голый `500` без тела | Диагностика только в `ScreenService/logs/AppLog.<дата>.txt` |
| Ответ SDK ожидается через `manualResetEvent.WaitOne(5000)` | Каждая команда — до 5 с в худшем случае. Типовая цепочка Delete+Upload+Send: ~1–2 с, худший случай ~15 с |
| `ScreenManager` сканирует IP из `ScreenScanSubnet` раз в **180 с** (первый раз через 1 с), таймаут коннекта **60 с** для одиночного IP и **1 с** для маски `10.77.1.*` | После старта сервиса экран может появиться в `GetDevices` не мгновенно. Не считайте пустой список фатальной ошибкой в первую минуту |
| Экран попадает в список только после получения DeviceInfo (`WaitDeviceInfo`) | `GetDevices` возвращает реальные `ScreenWidth`/`ScreenHeight` — **берите размер картинки оттуда, а не хардкодьте** |

## 3. Настройка перед интеграцией

### 3.1 Сеть

Контроллер сейчас на link-local адресе **169.254.255.254**, порт SDK **10001**.
На ПК с сервисом должен быть адрес из той же сети `169.254.x.x` на том же адаптере.

Проверка (PowerShell):

```powershell
Get-NetIPAddress -AddressFamily IPv4 | Where-Object { $_.IPAddress -like "169.254.*" }
Test-NetConnection 169.254.255.254 -Port 10001
```

Ориентируйтесь на **`TcpTestSucceeded : True`**. `PingSucceeded : False` — это норма,
контроллер не отвечает на ICMP.

> **Состояние стенда на 2026-09-05:** адаптер `Ethernet` = `169.254.211.213`,
> `169.254.255.254:10001` — **TcpTestSucceeded: True**. Экран на связи.

**Для продакшена:** перевести контроллер на нормальный статический IP через HDPlayer/HDSet
и прописать его в `ScreenScanSubnet`. Link-local — это аварийный режим (нет DHCP), он хрупкий.

### 3.2 `ScreenService/appsettings.json`

```jsonc
{
  "Kestrel": { "Endpoints": { "Http": { "Url": "http://localhost:8040" } } },
  "AppSettings": {
    "UseHttpsRedirection": false,
    "AccessToken": "7524e064a9b047eb896c99243b983010",
    "ScreenScanSubnet": [ "169.254.255.254" ]   // можно маску: "10.77.1.*"
  }
}
```

- `ScreenScanSubnet` — список IP или масок для поиска контроллеров.
- `AccessToken` — **обязательно сменить перед продакшеном**.
- `Url` — по умолчанию `localhost`, снаружи сервис недоступен. Если бэкенд парковки на другой машине,
  поменяйте на `http://0.0.0.0:8040` (и закройте nginx'ом / файрволом — своей авторизации, кроме токена, тут нет).
- Конфиг читается из **текущего каталога** (`Config.cs` → `AddJsonFile("appsettings.json")`),
  поэтому сервис надо запускать из его папки. `run.cmd` делает `cd /d "%~dp0"`.

### 3.3 Запуск

```cmd
ScreenService\run.cmd
```

`run.cmd` выставляет `DOTNET_ROLL_FORWARD=Major`, поэтому сборка под .NET Core 3.1 работает
на установленном .NET 8/10. Ждём в консоли строку вида:

```
05.09.2026 12:40:11  C16L-D24-00532: Connected (1)
```

Проверка живости:

```bash
curl -H "Authorization: Bearer 7524e064a9b047eb896c99243b983010" http://localhost:8040/api/Screen/Ping
# {"Message":"Pong"}
```

### 3.4 Авторизация

`SimpleAuthorizationMiddleware` закрывает **все** маршруты, включая `Ping`. Два способа:

```
Authorization: Bearer 7524e064a9b047eb896c99243b983010
```

или

```
?access_token=7524e064a9b047eb896c99243b983010
```

Неверный/отсутствующий токен → **401 с пустым телом**.
CORS открыт полностью (`SetIsOriginAllowed(_ => true)`) — API можно дёргать прямо из браузера,
в том числе со страницы, открытой через `file://`.

## 4. Протокол интеграции: 4 шага

Это и есть ответ на «как отправить сумму, время, QR и номер». База: `http://localhost:8040/api/Screen/`.

### Шаг 1 — узнать экран и его размер

```http
GET /api/Screen/GetDevices
Authorization: Bearer <TOKEN>
```

```json
[
  {
    "DeviceID": "C16L-D24-00532",
    "DeviceModel": "HD-C16L",
    "ScreenWidth": 160,
    "ScreenHeight": 160,
    "ScreenRotation": 0,
    "EthernetInfo": { "IP": "169.254.255.254", "Mask": "255.255.0.0", "IsAutoDHCP": false },
    "Connected": true
  }
]
```

Берём `DeviceID` и `ScreenWidth`/`ScreenHeight`. Пустой массив = сервис ещё не нашёл контроллер.

### Шаг 2 — удалить прошлую карточку

Обязательно, иначе `UploadFile` не перезапишет файл (см. §2).

```http
POST /api/Screen/DeleteFile
Content-Type: application/json

{ "DeviceID": "C16L-D24-00532", "FileName": "card.png" }
```

Первый раз файла нет — ошибку игнорируем.

### Шаг 3 — залить нарисованный PNG

```http
POST /api/Screen/UploadFile
Content-Type: application/json

{
  "DeviceID": "C16L-D24-00532",
  "FileName": "card.png",
  "Data": "iVBORw0KGgoAAAANSUhEUgAAAKAAAA..."
}
```

`Data` в C# объявлено как `byte[]`, а `System.Text.Json` десериализует `byte[]` из **base64-строки** —
поэтому сюда кладём PNG в base64 **без** префикса `data:image/png;base64,`.

### Шаг 4 — показать

```http
POST /api/Screen/SendImage
Content-Type: application/json

{
  "DeviceID": "C16L-D24-00532",
  "FileName": "card.png",
  "InEffect": 0,
  "OutEffect": 20,
  "InSpeed": 4,
  "OutSpeed": 4,
  "Duration": 600
}
```

- `InEffect: 0` — `IMMEDIATE_SHOW`, показать сразу без анимации.
- `OutEffect: 20` — `NOT_CLEAR_AREA`, не гасить область при зацикливании (иначе карточка мигает).
- `Duration: 600` — сколько секунд держать. Программа зациклена, так что это фактически «время до перерисовки».

## 5. Готовые реализации

### 5.1 Браузер — `screen-qr.html`

Самодостаточная страница (генератор QR встроен, зависимостей нет). Открывается по `file://`.
Форма: адрес сервиса, токен, номер, время, сумма, содержимое QR, длительность.
Кнопки: «Найти экраны» → `GetDevices` (размер экрана подставляется автоматически),
«Отправить на экран» → рисует canvas и выполняет Delete→Upload→SendImage,
плюс «Включить»/«Выключить экран» (`OpenScreen`/`CloseScreen`).

Годится как ручной пульт оператора и как эталон логики.

### 5.2 CLI — `send_parking_qr.py`

```bash
pip install qrcode pillow
export SCREEN_URL=http://localhost:8040 SCREEN_TOKEN=7524e064a9b047eb896c99243b983010

./send_parking_qr.py --plate "01KG777AAA" --amount 150 --qr "https://pay.example.kg/p/ABC123"
./send_parking_qr.py --plate "01KG777AAA" --amount 150 --qr "..." --time "12:35" --duration 600

# только отрисовать картинку, ничего не отправлять — удобно для отладки вёрстки
./send_parking_qr.py --plate "01KG777AAA" --amount 150 --qr "..." --preview card.png --no-send
```

Сам подтягивает размер экрана через `GetDevices`, сам делает Delete→Upload→SendImage.
Простейший способ подключить парковку — **дёргать этот скрипт из бэкенда** по событию оплаты.

### 5.3 Библиотека — `screenservice_client.py`

Обёртка над всеми методами API на голой stdlib (без зависимостей):

```python
from screenservice_client import ScreenService, Effect

ss = ScreenService("http://localhost:8040", "7524e064a9b047eb896c99243b983010")
dev = ss.devices()[0]["DeviceID"]

ss.delete(dev, "card.png")                 # обязательно перед upload
ss.upload_bytes(dev, "card.png", png_bytes)
ss.send_image(dev, "card.png",
              in_effect=Effect.IMMEDIATE_SHOW,
              out_effect=Effect.NOT_CLEAR_AREA,
              duration=600)
```

### 5.4 Прямая интеграция из любого бэкенда

Псевдокод для события «машина заехала / выставлен счёт»:

```python
def show_parking_card(plate: str, amount: int, pay_url: str):
    dev = get_first_connected_device()          # GetDevices, кэшировать на 1-3 минуты
    png = render_card(dev.width, dev.height,    # свой рендер: QR + 3 строки
                      qr=pay_url, plate=plate,
                      time=now("%H:%M"), amount=f"{amount} сом")
    api("DeleteFile", {"DeviceID": dev.id, "FileName": "card.png"}, ignore_errors=True)
    api("UploadFile", {"DeviceID": dev.id, "FileName": "card.png", "Data": b64(png)})
    api("SendImage",  {"DeviceID": dev.id, "FileName": "card.png",
                       "InEffect": 0, "OutEffect": 20, "Duration": 600})
```

Пример на curl (одна карточка целиком):

```bash
URL=http://localhost:8040/api/Screen
H="Authorization: Bearer 7524e064a9b047eb896c99243b983010"
JSON="Content-Type: application/json"
DEV=C16L-D24-00532

curl -s -X POST "$URL/DeleteFile" -H "$H" -H "$JSON" \
     -d "{\"DeviceID\":\"$DEV\",\"FileName\":\"card.png\"}"

curl -s -X POST "$URL/UploadFile" -H "$H" -H "$JSON" \
     -d "{\"DeviceID\":\"$DEV\",\"FileName\":\"card.png\",\"Data\":\"$(base64 -w0 card.png)\"}"

curl -s -X POST "$URL/SendImage" -H "$H" -H "$JSON" \
     -d "{\"DeviceID\":\"$DEV\",\"FileName\":\"card.png\",\"InEffect\":0,\"OutEffect\":20,\"Duration\":600}"
```

## 6. Раскладка карточки и читаемость QR

Логика одинакова в `screen-qr.html` и `send_parking_qr.py`. Карточка вертикальная, масштабируется
под любой `W×H`, полученный из `GetDevices`:

```
┌────────────────────────┐  y = max(1, H*0.01)
│   ███  ██ ███  ██ ██   │
│   █ █ ███  █ ████  █   │  QR: сторона = min(H*0.58, W*0.9),
│   ███  █ ███  ██ ███   │      чёрный на БЕЛОЙ подложке, по центру
│   █ ██ ███ ████  ███   │
├────────────────────────┤  top = y + сторона_QR + 1
│      01KG777AAA        │  строка 1: госномер   — жёлтый #FFDC00
│         12:35          │  строка 2: время      — белый  #FFFFFF
│        150 сом         │  строка 3: сумма      — жёлтый #FFDC00
└────────────────────────┘  фон — чёрный, высота строки = (H - top) / 3
```

Размер шрифта подбирается автоматически: берётся максимальный, при котором строка влезает
в `W - 2*pad` (`fitFont` в HTML / `_fit` в Python). Длинный номер просто станет мельче, а не обрежется.

### Читаемость QR — самое важное ограничение

Размер одного модуля QR в пикселях: `box = floor(min(H*0.58, W*0.9) / (модулей + 2))`.
Для экрана 160×160 (1 px = 4 мм, экран 640×640 мм):

| Длина payload | Версия QR | Модулей | `box`, px | Сторона QR | Физически |
|---|---|---|---|---|---|
| до 20 байт | v2 | 25 | **3** | 81 px | 324 мм |
| до 32 байт | v3 | 29 | **2** | 62 px | 248 мм |
| до 60 байт | v5 | 37 | **2** | 78 px | 312 мм |
| больше ~90 байт | v7+ | 45+ | **1** | — | не сканируется |

**Практический вывод:** держите ссылку оплаты короткой — короткий домен + короткий код
(`https://pay.kg/ABC123`, а не `https://parking.example.company.kg/payment/session?id=...`).
При `box = 1` один модуль QR = один светодиод = 4 мм, и телефон такой код уже не берёт.
Если ссылка длинная — используйте редирект-шортенер на своей стороне.

## 7. Смежные сценарии

### Вернуть «дежурный» экран после оплаты / по таймауту

Отдельной команды «очистить» нет — просто отправьте другое содержимое:

```jsonc
// вариант А: заставка-картинка (залита один раз, заранее)
POST /api/Screen/SendImage   { "DeviceID": "...", "FileName": "idle.png", "InEffect": 17, "OutEffect": 20, "Duration": 3600 }

// вариант Б: часы
POST /api/Screen/SendClock   { "DeviceID": "...", "ClockType": 0, "TimeDisplay": true, "TimeFormat": 0,
                               "TimeColor": "#FFFFFF", "TitleDisplay": true, "TitleText": "PARKING", "TitleColor": "#FFDC00" }

// вариант В: текст
POST /api/Screen/SendText    { "DeviceID": "...", "Text": "СВОБОДНО", "FontSize": 32, "Color": "#00FF00",
                               "BackgroundColor": "#000000", "InEffect": 0, "OutEffect": 20, "Duration": 3600 }
```

### Яркость день/ночь

```http
POST /api/Screen/SetLuminanceInfo
{ "DeviceID": "C16L-D24-00532", "Value": 40 }
```

`Value` 1–100, в коде зажимается в этот диапазон. Ставьте по расписанию (cron / Task Scheduler):
днём 80–100, ночью 20–40 — иначе ночью экран слепит, а днём не читается.

### Включить / выключить экран

```http
POST /api/Screen/OpenScreen   { "DeviceID": "C16L-D24-00532" }
POST /api/Screen/CloseScreen  { "DeviceID": "C16L-D24-00532" }
```

## 8. Подводные камни (обязательно к прочтению)

1. **`UploadFile` не перезаписывает файл.** Всегда `DeleteFile` перед `UploadFile`, иначе на экране
   останется старая карточка, а сервис молча вернёт 200. Это ошибка №1 при интеграции.
2. **Файлы копятся на флеш-памяти контроллера.** Не генерируйте имена вида `qr_<номер>_<timestamp>.png` —
   память кончится. Используйте одно-два фиксированных имени. Периодически сверяйтесь через `GetFiles`.
3. **Рекомендация для продакшена — «пинг-понг» из двух имён:** показываем `card_a.png`, следующую
   карточку заливаем как `card_b.png`, показываем её, а `card_a.png` удаляем. Так на экране никогда
   не бывает момента, когда отображаемый файл удалён.
4. **Каждая команда затирает экран целиком.** Ротация «QR ↔ бегущая строка» через API невозможна.
   Либо чередуйте вручную по таймеру со своей стороны, либо дорабатывайте `LEDScreen.Send`
   (несколько `HdArea` в одной `HdProgram`) — заготовка `AddProgram`/`UpdateProgram` в коде есть,
   но наружу не выведена.
5. **Все команды сериализованы глобальным локом.** Не шлите параллельно из нескольких воркеров —
   выстроится очередь. Один поток отправки на весь сервис.
6. **Ошибки безмолвные:** 401 и 500 приходят с пустым телом. Логи — `ScreenService/logs/AppLog.<дата>.txt`.
   При отладке держите это окно открытым.
7. **Неизвестный `DeviceID` → 200 OK и ничего не произошло.** Проверяйте, что `GetDevices` непустой
   и `Connected: true`, прежде чем считать отправку успешной.
8. **Размер картинки берите из `GetDevices`**, а не константой 160×160: при перенастройке экрана
   (другое число модулей) хардкод выдаст растянутую или обрезанную карточку.
9. **`Duration` — это не «время жизни» карточки.** Программа зациклена; по истечении `Duration`
   она просто начнётся заново. Убрать карточку можно только отправив что-то другое.
10. **Сервис слушает `localhost`.** Бэкенд на другой машине не достучится, пока не поменяете
    `Kestrel.Endpoints.Http.Url` на `http://0.0.0.0:8040`.
11. **Link-local `169.254.x.x` — временное решение.** Адрес выдаётся Windows автоматически при
    отсутствии DHCP; после перезагрузки или переключения кабеля связь может не подняться.
    Переводите контроллер на статический IP.

**Контроллер отвечает пустым `<out>` на все SDK-методы, кроме `GetIFVersion`.**
Снято TCP-снифером в разрыве сессии:

```xml
<!-- запрос -->
<sdk guid="64d5e7e8..."><in method="GetDeviceInfo" /></sdk>

<!-- ответ контроллера: ни result, ни данных -->
<sdk guid="64d5e7e8...">
    <out method="GetDeviceInfo"/>
</sdk>
```

Так отвечают **все**: `GetDeviceInfo`, `GetEth0Info`, `GetFiles`, `DeleteFiles`, `OpenScreen`, `AddProgram`.

Последствия по цепочке:

1. `SdkXmlDocument.ResolveXmlPacketData` не находит атрибут `result` → `Enum.Parse(null)` бросает →
   `ErrorCode.kUnknown`. Ответ не разбирается, даже если бы содержал данные.
2. `DeviceInfo` не заполняется → `LEDScreen.WaitDeviceInfo()` крутится в бесконечном цикле →
   экран **никогда** не добавляется в `_screens`.
3. `GetDevices` возвращает `[]`, а любой `Send*`/`UploadFile` тихо отдаёт **200 OK, не сделав ничего**.

**Итог визуальной проверки: на экране не появилось ничего** — ни `SendText`, ни `SendImage`.

### Как тестировали в обход

Чтобы проверить всю цепочку, между сервисом и контроллером был поставлен TCP-прокси
(`tools/sdk-proxy.js`), который подменяет только пустой ответ `GetDeviceInfo` на корректный,
а все остальные пакеты пропускает на реальный контроллер без изменений.

С прокси сервис зарегистрировал экран (`C16L-D24-00532: Connected (1)`), `GetDevices` заполнился,
все четыре запроса карточки вернули 200, файл дошёл до контроллера — **но изображение не появилось**.

Это разделяет ответственность: **ScreenService, наш рендер и HTTP-цепочка исправны;
не исполняет команды сам контроллер.**

### Дополнительная разведка устройства (2026-09-05)

| Проверка | Результат |
|---|---|
| MAC-адрес | `54:22:FD:07:45:70`. Префикс `54:22:FD` **не зарегистрирован в IEEE** (проверено по двум OUI-базам) — вендор по MAC не определяется. Типично для дешёвых китайских встраиваемых плат |
| Открытые TCP-порты | **22 (SSH), 10001, 10002**. Больше ничего — веб-интерфейса (80/8080) нет |
| Порт 10002 | Отвечает только heartbeat `0x0060`, хендшейк и команды игнорирует. Не альтернативный SDK-канал |
| UDP-поиск `kSearchDeviceAsk` (0x1001, порт 10001) | **Ответа нет.** Ни на unicast, ни на broadcast — вернулись только наши собственные пакеты. Штатный Huidu-контроллер на этот запрос отвечает `kSearchDeviceAnswer` со своим DeviceID |

Отсутствие ответа на UDP-поиск — важный симптом: обнаружение устройства реализовано в прикладной
части прошивки. Вместе с пустыми `<out>` и открытым SSH это складывается в картину
**«сетевой стек и базовый слой SDK живы, прикладная часть прошивки не обслуживает команды»**:
карта не настроена, не имеет конфигурации экрана, либо её приложение не запущено.

### Вероятные причины (в порядке правдоподобности)

1. **На карте не загружена конфигурация экрана.** Тогда она физически не может ни сообщить
   `screenWidth/Height` (отсюда пустой `GetDeviceInfo`), ни отрисовать программу.
2. **Отключён или запаролен сторонний контроль (SDK-сервис) в прошивке.** `GetIFVersion` —
   единственный до-авторизационный метод; всё после него молча отбрасывается. Картина совпадает точно.
3. **Карта занята другим управляющим подключением** — HDPlayer, HDSet или облачный/4G-клиент.
   Вторая SDK-сессия принимается, но команды игнорируются.

Важная деталь: ID `C16L-D24-00532` и `C16L-D24-0052A` в `CONTEXT.md` взяты из логов в исходном архиве —
значит когда-то `GetDeviceInfo` отвечал нормально. Это указывает на **изменение состояния/конфигурации
карты**, а не на несовместимость сервиса с этой моделью.

### Что делать дальше (на стороне железа)

1. Подключиться к карте через **HDPlayer / HDSet**, посмотреть её реальный DeviceID и параметры экрана.
2. Если конфигурация экрана пуста — загрузить её (P4, 8 модулей 320×160 мм → 160×160 px).
3. Проверить, включён ли сторонний контроль / SDK-сервис и не задан ли на него пароль.
4. Убедиться, что карту не держит другое ПО или облачный клиент — закрыть все прочие подключения.
5. Проверить питание и шлейфы приёмных карт: даже верная программа не будет видна при мёртвых модулях.
6. После этого повторить тест **без прокси** — `GetDevices` должен вернуть реальные ID и размер.

### Уточнение по итогам второго прогона (яркость + визуальная проверка)

Прогнан расширенный набор прямо на живой экран (через прокси, экран зарегистрирован):
`OpenScreen` → `SetLuminanceInfo=100` → сплошная красная заливка → крупный текст «1234» на синем → карточка.
Все команды **дошли до карты** (подтверждено снифером: `OpenScreen`, `SetLuminancePloy`, `GetLuminancePloy`,
`DeleteFiles`, `AddProgram`, файловые пакеты), файлы записались — но карта ответила пустым `<out>` **на каждую**,
включая яркость.

**Визуальный результат: на экране осталось старое содержимое, ни один тест не отобразился.**

Это ключевой факт, уточняющий диагноз:

- Экран **физически исправен** — модули, приёмные карты, питание и подсветка работают, раз старая программа видна.
- На карте **есть программа во флеш-памяти**, она непрерывно проигрывается.
- **Сломан ровно один узел: обработчик SDK-команд в прошивке завис.** Он отвечает на рукопожатие
  `GetIFVersion`, но не исполняет ни одну команду — ни новую программу, ни яркость, ни `OpenScreen`.
  Поэтому карта крутит последнюю успешно записанную когда-то программу и игнорирует всё новое.

Это не проблема сети, не проблема ScreenService и не проблема нашего рендера — это **состояние прошивки карты**.

### Рекомендуемое действие №1: перезагрузка контроллера по питанию

Зависшую встроенную службу в 9 случаях из 10 чинит перезагрузка. По сети карту не перезагрузить
(команда пойдёт в тот же мёртвый канал), поэтому нужно **физически**:

1. Снять питание с контроллера (или всего экрана) на ~10 секунд, включить обратно.
2. Дождаться, пока карта поднимется (~30–60 с).
3. Повторить тест. Признак, что помогло: `GetDevices` вернёт **реальный** DeviceID и размер
   (сейчас размер приходится подставлять прокси), а `<out>` пойдут с `result="kSuccess"`.

Если после перезагрузки поведение то же — карту нужно переинициализировать через **HDPlayer/HDSet**
(загрузить конфигурацию экрана и включить сторонний SDK-контроль) либо зайти на неё по **SSH** (порт 22
открыт, dropbear) с заводскими учётными данными и перезапустить приложение экрана.

### Результат перезагрузки (проверено 2026-09-05, 13:15)

Пользователь перезагрузил экран по питанию. После восстановления связи (порт 10001 поднялся сразу),
тест повторён в **прямом режиме** (без прокси):


Остаются три причины (все сохраняются в флеш-памяти карты и переживают ребут):

1. В настройках карты **выключен сторонний SDK-контроль** (third-party control). Самый вероятный вариант:

2. **Отсутствует или повреждена конфигурация экрана** (модульная раскладка, receiving-card mapping).
3. Приложение экрана в прошивке не инициализировано / не запущено.

**Вывод: без вендорского софта или SSH дальше не продвинуться — это подтверждено перезагрузкой.**

на самой карте.

### Финальный вывод

Карта **не исполняет SDK-команды как класс**, а не «зависла»:

(с правами администратора) показал, что HDPlayer управляет картой по **другому протоколу на TCP-порту 9527**.
Протокол вскрыт и повторён самостоятельным клиентом — карточка QR + номер + время + сумма реально
отображается на экране.

### Ключевые факты протокола 9527

- Обнаружение: карта сама вещает UDP-broadcast на порт 9527: `[0x01000000][0x0002]["C16L-B25-07457\0"]`.
  (Старый SDK искал по 10000/10001 форматом `0x1001` — карта на него не отвечает.)
- Кадр: `[len:2 LE][cmd:2 LE][payload]`, `len` включает заголовок. **Lock-step**: на `0xNNNN` карта отвечает `0xNNNN+1`.
- Сессия: рукопожатие (`0x000b/0730/0410/000d/040a/000f/0011/0013/0015`) → файлы
  (`0x0017` имя `<md5>.png` · `0x0019` данные ≤9212 Б · `0x001b`) → программа `.boo` (тот же файловый цикл)
  → финализация (`0x001d/001f`).
- Программа — XML нового формата HDPlayer: `HD_Controller_Plugin` → `HD_OrdinaryScene_Plugin` →
  `HD_Frame_Plugin(HD_Photo_Plugin)` → `HD_Photo_Plugin` со ссылкой `<ListItem MD5=.. FileKey="Photo"/>`.
  Экран 160×160, DeviceModel C16L, Rotation 2, id карты `C16L-B25-07457`. Картинка — PNG 160×160.

### Готовый инструмент — `tools/hd9527/`

Одна команда выводит карточку на экран:

```cmd
tools\hd9527\show-parking.cmd "01KG777AAA" "150 KGS" "https://pay.example.kg/p/ABC123" 12:35
```

Состав и детали — `tools/hd9527/README.md`. Зависимости: Node.js + Windows PowerShell (System.Drawing).
Бэкенд парковки вызывает этот скрипт по событию оплаты — номер/сумма/ссылка → карточка на экране.

### Что это значит для архивного ScreenService

`ScreenService` + `src/SDKLibrary` (порт 10001) с картой 2025 г. **не работают** — это подтверждено
исчерпывающе (§10). Рабочая интеграция — через `tools/hd9527/` (порт 9527). Если в будущем нужен REST-фасад
как у ScreenService, его надстраивают над `send9527.js`, а не над старым SDK.

## Приложение A. Справочник API

База: `http://localhost:8040/api/Screen/`. Заголовок `Authorization: Bearer <TOKEN>` обязателен везде.
`DeviceID` допускает несколько ID через запятую; пустой `DeviceID` в большинстве методов = «все экраны».

| Метод | HTTP | Тело | Назначение |
|---|---|---|---|
| `Ping` | GET | — | `{"Message":"Pong"}` |
| `GetDevices` | GET | — | список контроллеров с размерами и статусом |
| `UploadFile` | POST | `DeviceID, FileName, Data(base64)` | залить файл на контроллер |
| `DeleteFile` | POST | `DeviceID, FileName` | удалить файл |
| `GetFiles` | POST | `DeviceID` | список файлов на контроллере |
| `SendImage` | POST | `DeviceID, FileName, InEffect, OutEffect, InSpeed, OutSpeed, Duration` | показать картинку |
| `SendText` | POST | `DeviceID, Text, FontName, FontSize, Color, BackgroundColor, эффекты, Duration` | показать текст |
| `SendClock` | POST | `DeviceID, ClockType, Time/Date/Week/Title Display+Format+Color, TitleText` | показать часы |
| `SendVideo` | POST | `DeviceID, FileName` | показать видео (асинхронно) |
| `SetLuminanceInfo` | POST | `DeviceID, Value (1–100)` | яркость |
| `GetDeviceFontInfo` | POST | `DeviceID` | шрифты на контроллере |
| `OpenScreen` / `CloseScreen` | POST | `DeviceID` | включить / выключить экран |

Полное описание — `ScreenService-API.md`, машиночитаемое — `screenservice-openapi.yaml`
(импортируется в Postman/Swagger).

## Приложение B. Коды эффектов (`EffectType`)

| Код | Эффект | Код | Эффект |
|---|---|---|---|
| 0 | показать сразу | 16 | вертикальное закрытие |
| 1–4 | сдвиг влево / вправо / вверх / вниз | **17** | **плавное появление (fade)** |
| 5–8 | перекрытие влево / вправо / вверх / вниз | 18–19 | горизонтальные / вертикальные жалюзи |
| 9–12 | перекрытие из углов | **20** | **не очищать область** |
| 13 | горизонтальное разделение | 21–24 | непрерывное движение (бегущая строка) |
| 14 | вертикальное разделение | **25** | **случайный эффект (по умолчанию в API)** |
| 15 | горизонтальное закрытие | 26–29 | непрерывное движение «встык» |

Для карточки парковки: **`InEffect: 0`, `OutEffect: 20`** — мгновенный показ без мигания при зацикливании.
